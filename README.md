# Частина D. Висновки
D.1. Неочевидним з поведінки сервера виявилося те, що при зверненні до домену example.org фактична відповідь повертається не від кінцевого вебсервера, а з кешу проміжного вузла мережі доставки контенту (CDN). На це конкретно вказують рядки заголовка X-Cache: HIT та велике значення поля Age: 512394 під час виконання завдання А.1.

D.2. Найбільше утруднення при визначенні походження викликало поле Server: ECS (dcb/7EEB). Традиційно заголовок Server генерується кінцевим вузлом, що обслуговує логіку сайту. Однак абревіатура ECS (Edge Cache Server) вказує на те, що цей заголовок, найімовірніше, був змінений або повністю перезаписаний проміжним сервером CDN під час кешування відповіді.

D.3. Після виконання роботи без відповіді залишилося питання про те, як саме проміжні вузли (кешуючі сервери) обробляють конвеєрні запити (pipelining) — чи скидають вони з'єднання після видачі першої помилки 404, якщо другий ресурс був знайдений у їхньому кеші.
# Контрольні питання
1. У завданні A.1 сервер не надсилав відповіді, доки не було введено порожній рядок. Чим це зумовлено?
Протокол HTTP вимагає, щоб блок заголовків завершувався порожнім рядком, що складається з послідовності повернення каретки та переведення рядка (\r\n\r\n). Сервер очікує на цей маркер, щоб зрозуміти, що клієнт завершив передачу заголовків і готовий до отримання відповіді.
2. Порівняйте результати завдань A.1, A.2 та A.3.1–A.3.3 (таблиця Додатка Д). За яких значень поля Host і за якої версії протоколу сервер обслуговує запит, а за яких — ні? Яку задачу розв'язує поле Host?
 Відповідь має посилатися на конкретні рядки ваших виводів.Поле Host розв'язує задачу маршрутизації — воно дозволяє серверу визначити, до якого саме сайту (віртуального хоста) звертається клієнт, оскільки на одній IP-адресі може розміщуватися безліч доменів. У версії HTTP/1.1 наявність поля Host є обов'язковою: без нього сервер повертає помилку (вивід A.2: HTTP/1.1 400 Bad Request), а з чужим або недійсним хостом — відмовляє в доступі (виводи A.3.1 та A.3.2: HTTP/1.1 404 Not Found). Однак у версії HTTP/1.0 сервер коректно обслуговує запит без цього поля (вивід A.3.3: HTTP/1.0 200 OK).
3. Скільки відповідей надійшло у завданні A.4 і з якими кодами стану? Чи залежить відповідь сервера на порту 80 від запитаного шляху — і що це говорить про роль цього сервера?
Якщо надійшла одна відповідь, знайдіть у ній поле заголовка, яке це пояснює, або зазначте, що такого поля немає. Якщо надійшло дві — що це означає для клієнтської програми, яка завантажує сторінку з великою кількістю вкладених ресурсів?У завданні А.4 надійшло дві окремі відповіді в межах одного TCP-з'єднання: перша з кодом 404 Not Found (на хибний шлях) і друга з кодом 200 OK (на кореневий каталог). Це демонструє підтримку сервером HTTP-конвеєризації (pipelining). Для клієнтської програми (наприклад, браузера), яка завантажує сторінку з великою кількістю картинок і скриптів, це означає можливість відправити відразу кілька запитів і отримати їх асинхронно, не витрачаючи час на встановлення нових TCP-з'єднань для кожного вкладеного ресурсу.
4. Які поля заголовка програма curl додала самостійно (завдання A.5)? Ці поля не є обов'язковими — сервер відповів і без них у завданні A.1. З якою метою їх додано?
Програма curl самостійно додала заголовки User-Agent: curl/7.81.0 та Accept: */*. Поле User-Agent використовується для ідентифікації клієнта (щоб сервер міг зібрати статистику або адаптувати верстку), а поле Accept інформує сервер про те, що клієнт готовий прийняти будь-який формат медіаконтенту.
5. За якими ознаками у вашому виводі виявляється присутність проміжного вузла?
Якщо таких ознак не виявлено, поясніть, що з цього випливає.Присутність проміжного вузла (CDN) явно підтверджується наявністю заголовка X-Cache: HIT, який сигналізує про видачу ресурсу з кешу. Додатковим підтвердженням є поле Age: 512394, що показує, скільки секунд ця відповідь зберігалася на проміжному сервері перед відправленням клієнту.
